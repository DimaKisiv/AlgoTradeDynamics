# Demo script для захисту

Орієнтовна тривалість: **8–10 хвилин**. Послідовність побудована так, щоб комісія побачила
від маркетингового вигляду продукту до глибини технічної реалізації.

## 1. Вступ (30 сек)
- Хто я і що це за проект.
- Одна фраза проблеми: «Багато трейдерів-початківців втрачають гроші тому, що не тестують
  свої стратегії перед використанням реальних коштів. Готових простих рішень для безпечного
  backtesting небагато і вони дорогі або складні.»

## 2. Лендинг (1 хв)
- Відкрити http://localhost:5173/
- Прокрутити Hero → Features → HowItWorks → Strategies → CTA.
- Звернути увагу комісії на: преміальний дизайн (Apple-style typography, glassmorphism,
  reveal-анімації, готовий SVG-preview графіка в Hero).
- Тут пояснити: «UI — це обличчя продукту. Робота над дизайном — це окрема третина цього MVP».

## 3. Backtest Engine (3–4 хв)
- Перейти на `/app`.
- Залишити параметри за замовчуванням (BTC/USDT, $10 000, MA 10/30, risk 20/5/25).
- Натиснути «Запустити backtest».
- Показати, як справа з’являється результат: метрики, equity curve з анімацією, журнал угод.
- Підкреслити пояснення метрик:
  - **Total PnL** — фінансовий результат
  - **Win Rate** — відсоток прибуткових угод
  - **Max Drawdown** — найбільший просад капіталу за весь період
- Змінити стратегію на **RSI Mean Reversion** і запустити знову. Показати інший набір угод.
- Запустити третій раз з агресивними параметрами (наприклад position_size = 80%,
  stop_loss = 2%) — продемонструвати, як бот зупиняється через `Max drawdown limit`.

## 4. Історія запусків (1 хв)
- Перейти на `/runs`.
- Усі попередні запуски в списку. Клік по будь-якому → `RunDetailPage`.
- Зайти в найперший запуск, показати збережені параметри (зліва) і повний результат знизу.
- Підкреслити: дані персистентні, зберігаються в PostgreSQL.

## 5. API під капотом (1 хв)
- Відкрити http://localhost:8000/docs (Swagger UI).
- Показати: 6 endpoints, повна OpenAPI-документація автогенерована з Pydantic-схем.
- Опційно: розгорнути `POST /api/backtests/start` і показати схему request/response.

## 6. Архітектура коду (1.5 хв)
Швидко показати в IDE структуру:

- `backend/app/bot_engine/strategies/` — два класи стратегій, абстракція `Strategy`.
- `backend/app/bot_engine/backtester.py` — серце симуляції, з ризик-менеджментом.
- `backend/app/services/backtest_service.py` — оркестрація, тут перетинаються бот і БД.
- `backend/app/api/backtests.py` — тонкий HTTP-шар.
- `backend/tests/` — 21 тест, можна запустити в терміналі: `pytest -v`.

Підкреслити: **чисте розділення відповідальностей**. Бот-двигун — pure Python, його можна
переносити, тестувати, заміняти на live trading без зміни решти системи.

## 7. Завершення (30 сек)
- Що зроблено: повний цикл — від UI до БД, дві стратегії, 21 тест, Docker.
- Що далі (у пояснювальній записці): live trading через `ccxt`, ML-сигнали, multi-user
  з аутентифікацією, портфоліо з кількох стратегій.

## Можливі питання комісії і короткі відповіді

| Питання | Відповідь |
|---|---|
| Чому Python для бекенду, а не Node? | Уся торгова екосистема в Python (pandas, ccxt, vectorbt); FastAPI не повільніший за Express; команда не хоче два бекенд-сервіси. |
| Чому SQLAlchemy, а не raw SQL? | Type-safety, автоматичне CASCADE через relationships, інтеграція з Alembic. |
| Як ви зберігаєте параметри стратегії? | У JSON-колонках. Це дозволяє додавати нові стратегії без зміни схеми БД. |
| Що буде, якщо backtest падає на середині? | `db.commit()` тільки після успішного завершення. Якщо викид — транзакція не зафіксована, журнал залишається консистентним. |
| Як тестуєте бота? | Unit-тести з реальним CSV-датасетом + buy-once stub для тестування ризик-лімітів. |
| Як ви замикаєте позицію в кінці датасета? | У `backtester.run()`: якщо позиція відкрита після останньої свічки — закриваємо за `last.close` з `reason="End of dataset"`. |
| Чи реальні це біржові дані? | У MVP — генерований реалістичний датасет (366 днів) для відтворюваності. У `data_loader.py` контракт CSV простий; у production підключається `ccxt`-завантажувач. |
